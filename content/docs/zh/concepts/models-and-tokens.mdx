---
title: 模型与 Token
description: 理解模型名称、输入 token、输出 token、上下文和费用
---

模型决定了这次请求由哪个 AI 能力处理。Token 则是模型读写文本时使用的基本计量单位。

## 模型是什么

模型名称通常写在请求体里的 `model` 字段中：

```json
{
  "model": "gpt-5.4",
  "messages": [
    { "role": "user", "content": "用一句话介绍你自己" }
  ]
}
```

不同模型适合不同场景：

| 场景 | 推荐方向 |
| --- | --- |
| 日常聊天、总结、翻译 | 选择速度快、成本低的通用模型 |
| 编程、代码理解、自动修改 | 选择代码能力更强的模型 |
| 长文档分析 | 选择上下文更长的模型 |
| 知识库、检索、RAG | 选择 embedding 模型 |

实际可用模型以 `GET /v1/models` 返回结果为准。

## Token 是什么

Token 可以粗略理解为模型处理文本时的“片段”。中文、英文、标点、空格都会被拆成 token。

一次调用通常会产生两类 token：

| 类型 | 含义 |
| --- | --- |
| 输入 token | 你发给模型的内容，包括系统提示词、用户问题、上下文、历史对话 |
| 输出 token | 模型生成的回答 |

费用、速度、上下文长度通常都和 token 数量有关。

## 上下文是什么

上下文是模型在一次请求里能看到的全部内容。它可能包括：

- 系统提示词
- 当前用户问题
- 历史对话
- 传入的文档片段
- 工具调用结果

上下文越长，输入 token 越多，请求成本和延迟通常也会增加。

## 为什么同一个问题费用可能不同

因为费用通常不只看问题长度，还看：

- 是否带了历史对话
- 是否塞入了长文档
- 模型回答是否很长
- 是否开启多轮工具调用
- 使用的是哪个模型

## 实用建议

- 客户端用户先用推荐模型，不要一开始就随便填模型名。
- 开发者在产品里要控制上下文长度，不要无脑把所有历史记录都塞进去。
- 长文档场景优先做摘要、分段或检索，再交给模型处理。
- Embeddings 模型只负责生成向量，不直接回答聊天问题。
